# 情报结果自主校验方法论

最后更新：2026-08-19

定位：**结果校验类工作是 Agent 的自主职责，默认不反问用户**。凡能自查的
（弹幕信号共振、流量骤降、多源交叉、比分源核对）一律自主闭环完成；
只有外部权威信息缺失时才标"待官方确认"——那是状态标注，不是提问。
本方法论全项目通用（弹幕情报、交易状态、扫描结果、复盘结论）。

## 一、自主校验原则

```text
1. 默认自主：比赛结束/比分/状态/结果类判定由 Agent 独立完成多信号验证并落库，
   不把用户当校验器；除非信息源本身不存在（如官方还没出结果）。
2. 宁可保守不放大：低置信一律写"进行中/待确认"，绝不把预测当结果；
   不夸大信号强度，不把单点异常扩散成结论。
3. 先自查再回应：用户对数据提出异议时，先怀疑工具/方法、先交叉验证、
   先查根因，再回应（防错规则第 6 条）。
4. 错误可修正不扩大：误判按"误判修正"流程回退+留痕+同步修正相关文档；
   修正记录用于改进方法，不扩散传播。
```

## 二、多信号共振校验框架

```text
结束/结果判定需 ≥3 类独立信号共振（细节见 DANMU_CAPTURE_RULES 第 12 节）：
  a) 结束语高密度：GG/恭喜/拿下类连续 ≥2 分钟高密度，且用户数 ≥5；
  b) 比分/图数核对：显式"X 2:0 Y"式陈述与直播画面/流标题/官方比分源对照；
  c) 流量骤降：窗口密度降到峰值 <10% 并持续 ≥5 分钟；
  d) 官方/第三方源：赛事官网、HLTV、官方房间标题、主播明确宣布。
语言甄别：过去式+共识+无修饰 = 结果陈述；"要赢/必/不意外/就离谱/该赢/有说法"
  = 预测/玩梗，一律不算结果。
灰话词典（2026-08-22 教训）："赚了/吃一局/收米/收钱/送温暖/水位不动/明演/
  到点就送/包翻/剧本/卡盘"= 盘口/做局质疑词，禁止当胜负信号；灰话密集时结果
  判定必须另找独立信号（恭喜/拿下/比分/官方）并标注低置信。
低样本门槛：单源且比赛窗口弹幕 <800 条 → 结果一律"低置信·待确认"。
多源交叉：≥2 个直播间同场观点重合才升置信；单源零散弹幕 = 待确认。
工具：tools/verify_match_end.py 打分，<3/4 一律输出"未确认（进行中）"。
```

## 二.5 官方结果快速通道（2026-08-23 固化，省 token/省时）

```text
结果确认按优先级执行，命中即停，不重复搜索：
  P0 Polymarket 结算（首选）：结算价即官方结果。跑
     python3 tools/verify_match_result.py --match-id <id> [--apply]
     （gamma /events?slug= 的 closed + outcomePrices；无需网页）。
  P0.5 Riot 官方赛事 API（LoL，2026-08-27 起）：选手×英雄/局结果权威数据。
     跑 python3 tools/fetch_official_game_data.py --league lck --date <date> --teams A,B
     （esports-api getSchedule/getEventDetails + feed.lolesports.com window；
     BP 阶段 window 空，开局后即有；接口与 leagueId 见 knowledge/OFFICIAL_DATA_SOURCES.md）。
  P1 官方直播间/赛事房间标题（采集时顺手记录）。
  P2 固定站点批量搜索：一次 search 调用 5 个查询；snippet 可定案就不 open_page；
     战报 URL 有规律时直接拼 URL 取多场。
  P3 弹幕多信号兜底（verify_match_end.py），标"弹幕口径·待官方"。
触发：终局信号 → P0；P0 无事件 → P0.5（LoL 小局/阵容先于此）→ P1 → P2 → P3。
阵容/选手×英雄类校验：只走 P0.5 / 官方战报，禁止用弹幕配对（D8）。
历史缺口：每日批量跑一次 verify_match_result.py 扫全部待确认记录。
已确认不重查；每场只留一行可溯源来源（结算 slug / 战报链接）。
```

## 三、灰信号与"剧本"世界观（不放大错误）

```text
1. 世界有很多剧本：把"剧本/做局/假赛/卡盘"作为可观察的叙事信号，
   只做风险标注与盘口对照素材，绝不当结论（纪律红线，全项目适用）。
2. 灰信号价值 = 可验证资产：质疑条数 × 时间集中度 × 盘口重合度 × 结果对照，
   用于统计"质疑→兑现率"，不单独作为交易依据。
3. 有价值数据优先：优先沉淀可验证资产（预测验证、联赛规律、密度峰值×价格、
   灰信号×盘口对照、选手/队伍画像）；噪音与玩梗只归档不展开。
4. 注意细节：词表漏抓、断档缺口、时间窗口错位、比分误判都要记录与修正；
   但修正聚焦数据本身，不放大为系统性失败。
5. 凡走过必有痕迹（2026-08-19）：涉事队伍/选手一旦被灰信号标记，即进入
   重点跟踪名单，长期留痕（docs/data/intel/gray_entities.json）；再犯自动升级
   关注等级。库内实体在 teams.json/players.json 同步 gray_history 字段，
   后续比赛出现同类质疑时预警等级自动提升一档。
6. 灰信号双用途分层（2026-08-22 用户确认，重要）：灰信号在两层中作用不同——
   a) 结果校验层：灰话/质疑禁止作为"谁赢了"的事实证据（赚了/吃一局/水位不动
      等为做局灰话，语义可能反向）；该层禁用只为防误判，与价值无关；
   b) 决策层：灰信号是核心操作资产——"被质疑侧 = 价格可能失真"，
      以方向兑现率统计 + 再犯状态 + 盘口价位加权，形成反向/对侧操作候选；
   c) 两层不冲突：判定事实看独立信号（恭喜/拿下/比分/官方），
      决定操作看灰信号模式与兑现率。页面需同时标注"结果口径"与"操作视角"。
```

## 四、自主闭环流程（结果校验）

```text
1. 候选结束时刻 -> 跑 tools/verify_match_end.py；
   评分 <3 分 = 未确认，继续监控（不落结果）。
2. 评分 ≥3 分 -> 查官方/比分源交叉 -> 回填 matches.json（带来源标注：
   "弹幕口径（多信号共振）"或"官方确认"）。
3. 同步 teams / players / gray_signals / leagues + 报告 + 索引 + DANMU_INTEL；
   官方结果到达后自主回填 pending -> confirmed。
4. 校验质量回测：定期统计误判数/总数与原因，反哺词表与阈值；
   新联赛/新比赛类型先登记词表再分析（防静默漏抓）。
5. 每场比赛结束先出"状态确认"（自主），再出"整场复盘"（如有价值数据）。
```

## 五、红线

```text
1. 灰信号不作假赛结论（只作风险标注）。
2. 官方确认前，result 必须带"待确认/弹幕口径"标注，禁止写成既定事实。
3. 校验工具结果与官方/比分源冲突时，以官方/比分源为准并回退弹幕口径。
4. 用户明确给出结果时，以用户为准并核对数据口径（先自查差异）。
5. 英文 Twitch 弹幕反讽识别（2026-08-25 固化）："FNC ARE BACK"/"HOLY X"/
   "X is playing well.. mhm" 等多为反讽或玩梗，必须先做语气判定；与比分机器/
   官方比分源冲突时，以结构源为准并标注分歧（教训：FNC-NAVI G1）。
```

## 五bis. 结果判定门禁（2026-08-25，强制工具）

```text
任何"已结束/比分/系列终局"结论在输出复盘页或落库前，必须执行：
  python3 tools/match_state_guard.py --start <UTC开赛> --now <UTC现在> \
      --scorebot "TS:比分行" --danmaku "TS:弹幕行"
四道闸：时间门槛（<30 分钟禁判结束）/ 结构源优先（仅弹幕=pending）/
  反讽识别（ARE BACK/HOLY X/playing well.. mhm 等不作证据）/
  比分源滞后（>5 分钟降级）。系列终局须 2-0/2-1 类比分或官方积分榜，
  1-0/1-1 只是局末。门禁不过 = 情报未交付（与 MD 镜像同级）。
回归：tests/test_match_state_guard.py（E1-E6）。
```

## 六、情报价值提炼标准（2026-08-20，防"噪音页"）

```text
背景：CS-R2 页面一度只有"比分同步/某人被批"式噪音，用户批评"看不到有用信息"。
规则：情报页/复盘必须回答"这份情报对决策有什么价值"，按高价值维度提炼，
  禁止只堆原始统计、单条弹幕或低信息量描述。
高价值维度清单（按优先级）：
  1. 阵容/换血动态：转会、被踢/新援、阵容变动叙事（观众"踢对/踢错"共识）——
     直接改变队伍强弱预期，价值最高；
  1b. BP/选人情报：熟练度质疑、异常选角、教练责任、观众"BP 判负/判胜"预测
      （见 knowledge/BP_INTEL.md；CS 对应图池/选边）；
  2. 队伍状态：换人后变强/变弱、状态差/好（如"换完阵老鼠没以前强了"）；
  3. 关键选手状态：明星位 carry/低迷、老将表现（与盘口直接相关）；
  4. 地图池与强图弱图：自选图、强图兑现（如 FUT 图三强图）；
  5. 比分/赛点/加时等局势信号：谁领先被翻、赛点、OT（标注未确认）；
  6. 观众共识/分歧：可验证的预测锚点（如"打满 vs 2-0"）；
  7. 灰信号/异常：只作风险标注，注明甄别（如"买"类=转会/买枪非灰信号）；
  8. 对后续比赛/盘口的含义：一句话落点（如"MOUZ 状态差→后续看空"）。
每个页面至少覆盖 1/2/5/8；有换血动态时必须覆盖 1。
```
