# 虎牙弹幕抓取规则与交易模式（知识库）

最后更新：2026-08-19

本文沉淀"弹幕 -> 交易情报"的完整工作流：抓取规则、数据规范、分析维度、
交易应用模式与红线。新会话按本文执行，先读 knowledge/DANMU_INTEL.md 与
DANMU_USERS.md 了解数据与人员档案。

## 1. 抓取规则（什么时候开、什么时候停）

```text
开抓时机：博主开播且正在解说比赛时（直播页面标题含"XX vs XX"、弹幕讨论比赛内容）。
停抓时机：比赛结束（弹幕出现"GG/结束/下班"或观众讨论下一场时）即停，等下一场再开。
直播间清单：STREAMER_PROFILES.md（957 / 毛毛 / 米勒 / 硕硕）；按需扩展。
数据落盘：docs/data/danmu/<博主>/<日期>_<房间>.jsonl（JSONL 一行一条）。
字段：ts（秒级时间戳）/ nick（昵称）/ uid / text（内容）/ source（稳定来源）/ room_id。
```

## 2. 抓取工具与运行环境

```text
工具：tools/fetch_huya_danmu.py（实时 WebSocket，纯 Python，无浏览器无逆向）。
依赖：复用 /tmp/real-url（GitHub wbt5/real-url）的虎牙 Tars/WebSocket 实现；
  运行环境 /tmp/intel-whisper-venv（aiohttp / requests / pycryptodome）。
命令：PROTOCOL_BUFFERS_PYTHON_IMPLEMENTATION=python \
  /tmp/intel-whisper-venv/bin/python tools/fetch_huya_danmu.py \
  --url <直播间> --out <jsonl>        # 0=持续到 Ctrl-C
注意：PROTOCOL_BUFFERS_PYTHON_IMPLEMENTATION=python 必须带（绕过旧 protobuf）；
  断线自动重连（客户端内置）；禁止同时跑两个抓取进程写同一文件（实测会混行）。
生产入口：tools/run_danmu_session.py；每房状态写入
  runtime/danmu_sessions/<session>/<source>.status.json，异常退出由父进程自动重启。
```

## 3. 分析维度与工具

```text
tools/danmu_intel.py：提炼 队伍情绪 / 选手状态 / 盘口数字 / 局势线索 /
  灰信号 / 弹幕密度峰值，输出 runtime/danmu_intel.json。
tools/danmu_report.py：生成 SAP/Apple 风格 HTML 简报（reports/intel_danmu_*.html）。
画像沉淀：队伍 -> TEAM_PROFILES.md；选手 -> DANMU_INTEL.md 记录；
  高价值用户 -> DANMU_USERS.md。
```

## 4. 交易应用模式（弹幕怎么变成交易情报）

```text
1. 弹幕密度峰值 = 比赛关键时刻：高活跃分钟（>=均值+2σ 且 >=6 条）通常是
   团战/翻盘/争议事件，与 Polymarket 价格异动强相关——作"事件检测"信号，
   后续与价格序列对照（待接入）。
2. 信息差信号：观众"嘴上看衰" vs 比分/盘面领先的分裂（如 TH 被看衰却赢 FNC、
   或 TH 0:2 被横扫但让分盘被讨论）——提示市场情绪与实力判断错位。
3. 盘口讨论：观众直接聊让分/人头盘（-6.5 / 8-2 / 总人头），反映大众关注点，
   与 Polymarket 让分/胜负盘情绪对照。
4. 高价值用户跟踪：DANMU_USERS.md 中的专业用户（TokyoLll / LuLu13 等）观点
   作为可聚合的"准信源"，跨场次累计可信度。
5. 版本/赛区观察：如"中路大核刷钱、LEC 不打架"——影响比赛形态与策略路由。
```

## 5. 红线与纪律

```text
1. 弹幕低可信度、需聚合：单条不算信号，>=3 条同向才作参考。
2. 灰信号 = 集体智慧信号（2026-08-18 升级）：直播间梗（小卖部/健身房/接=接广告）
   是噪音；"假赛/剧本/菠菜/卡盘"类质疑是**有价值的观众集体信号**——
   聚合计数 + 时间分布 + 与盘口/价格对照，标注"观众质疑，非结论"；
   质疑集中且伴随盘口异常时，作为风险升级提示，仍不直接当作假赛证据。
3. 区分多场比赛：弹幕会同时聊多场（如 LEC 场里出现 LCK/其他队名），
   局势分析必须严格限定当前场，跨场信息单独归类。
4. 比赛识别存疑时标注：比分/结果从弹幕推断时写"据弹幕推断，待官方确认"。
5. 弹幕只作情报参考，不改变止损/止盈纪律（与 D5 一致）。
6. 比赛结束即停抓，不长时间空跑。
7. 市场存在性检查：先确认比赛在 Polymarket 有市场再做价格对照
   （LEC 等无市场比赛只做情报沉淀，见 DANMU_POLYMARKET_ROADMAP.md）。
```

## 6. 赛制常识（影响局势判断）

```text
- LEC 近期 BO3 无 1-1、只有 2-0（用户确认 + 弹幕印证"最近lec都没有11，都是20"）。
- 低人头/放资源/保枪打法在 LEC 常见（版本：中路大核刷钱，除 LPL 外不打架）。
- 弹幕中"8-2"、"10个头"等为人头盘/总击杀讨论，不是小局比分。
```

## 7. SOOP 抓取补充规则（2026-08-18）

```text
1. 实时链路：tools/fetch_soop_danmu.py（自研二进制聊天协议，只取弹幕文本/
   用户 ID/昵称）。聊天服务器 IP 直播中会轮换，脚本自动重连续写同一 JSONL；
   长时间无新数据时先查重连日志，禁止直接报"无弹幕"。
2. 历史回捞：整场直播结束后 VOD 生成，用 tools/fetch_soop_vod_chat.py
   按 ChatLoadSplit 分片翻页回捞全量历史弹幕；直播进行中无法拿已过去的弹幕，
   缺的时段等 VOD 后补齐（标记 soop_vod 数据源 + vod_time_sec）。
3. 韩文处理：抓取原样存韩文；分析阶段做翻译与词表（NS=농심 等），
   词表覆盖不到的队伍/选手会静默漏掉，需定期扩充（与虎牙规则一致）。
4. 空结果自检：VOD 回捞 0 条时检查 rowKey 是否 _c 后缀、总时长字段、
   是否还在直播（未生成 VOD）——禁止直接下"无历史弹幕"结论。
5. 时段切片：多局制比赛按 vod_time_sec 切局（第一局 ≈ 开场后 40-60 分钟），
   用直播弹幕的 unixtime 与 VOD 时间戳对齐时注意延迟与转场。
```

## 8. 多直播间并发规则（2026-08-18）

```text
1. 统一入口 tools/fetch_danmu_multi.py --rooms "<url1>,<url2>,..."
   （虎牙按房间号 https://www.huya.com/<room>，SOOP 按
   https://play.sooplive.com/<bj>/<broad_no>），每房间独立子进程、
   独立 JSONL 落盘 docs/data/danmu/<平台>/<日期>_<标识>.jsonl。
2. 直播间注册表（数据库留档）：docs/data/danmu/streamer_registry.json，
   含平台/房间号/uid/关注赛事/采集状态/优先级；档案文档
   knowledge/STREAMER_PROFILES.md 与之同步。新增直播间先登记再采集。
3. 已实测并发：虎牙 957（890001）+ SOOP LCK_CL 同时抓取互不影响；
   虎牙各房间协议统一（protobuf 环境变量已内置到工具）。
4. 同一场比赛多直播间同时抓 = 交叉验证（观点重合/分歧），
   报告里标注信号来源直播间（如 957 vs 硕硕同场）。
5. 并发数量上限建议 3-4 个房间/次（轻量 WebSocket，实际资源占用极小，
   但便于人工盯盘与停开管理）；比赛开场前开、赛后停。
6. 持续会话必须检查 page_live / heartbeat_at / last_message_at / restart_count；
   页面开播但 120 秒无首条弹幕标记 live_no_danmaku_alert，禁止解释成“无信号”。
7. 新会话先读 runtime/danmu_sessions/<session>/session.json；状态仍新鲜且 running 时不得重复启动。
```

## 9. 结构化情报库同步规则（2026-08-18，最高优先级沉淀层）

```text
1. 统一情报库目录：docs/data/intel/（JSON，可查询、可长期积累）：
   leagues.json      联赛维度（特征/灰信号风险/平台/词表）
   teams.json        队伍画像（弹幕情报 + 盘面情报 + 信任等级）
   players.json      选手画像（角色/焦点英雄/情绪/待确认项）
   matches.json      比赛记录（结果推断/关键信号/数据文件/报告链接）
   users.json        高价值用户（跨平台聚合/分型/可信度）
   gray_signals.json 灰信号记录（质疑条数/时间窗/盘口对照，非结论）
2. 每场比赛分析完成后，必须同步更新对应 JSON（与 DANMU_INTEL.md 同批落盘），
   禁止"报告出了但情报库没更新"（与数据同步约定一致）。
3. 新维度（如英雄/版本/盘口）先登记 schema 再使用；字段以官方名单为准时
   标注 pending。
4. 用户正在自建外部情报库，本库为其数据源之一——字段命名与更新频率
   保持稳定，便于对接。
```

## 10. 标准工作流与工具排障（2026-08-19）

```text
1. 弹幕任务统一按 knowledge/DANMU_WORKFLOW.md 五阶段 SOP 执行，
   不再临时拼凑命令；会话托管首选 tools/run_danmu_session.py。
2. 已知故障（已修，2026-08-19）："房间页缺少 profileRoom/lChannelId"——
   根因是 fetch_room_info 抓移动页却检查桌面页字段；已改抓 www 桌面页并
   回退 channel_id。遇同类报错：先 curl 页面看字段，再改工具，不猜页面失效。
3. 每次工具修复，在本文"常见故障"登记（防错规则：先怀疑工具）。
4. 已知故障补充（2026-08-19）：部分房间页把 profileRoom/lChannelId 序列化为
   带引号字符串（如 uid 1199652774074 / 房间 321123 别名 captainmo），
   正则只认纯数字导致误报"房间页缺少字段"；已改为容忍可选引号
   （r'"profileRoom":\s*"?(\d+)"?'）。遇新房间报错：先看页面该字段是数字还是
   字符串，再决定改正则还是页面真的失效。
5. 已知故障补充（2026-08-20）：SOOP 弹幕 JSONL 的 ts 是字符串
   （"2026-08-20T...+0800"，另有 unixtime），danmu_intel.analyze 直接做
   ts 减法/整除导致"unsupported operand '-' between str and str"崩溃，
   聚合监控反复重启；已加 _ts_value() 统一转 epoch（unixtime 优先，否则解析
   字符串）。同批修复：SOOP 字段 message/nickname 与虎牙 text/nick 不一致
   （analyze 入口归一化 text，top_users 兼容 nickname/user_id）。遇混合平台
   监控报同类错，先查字段/类型再改工具。
```

## 11. 比赛维度处理规则（2026-08-19，弹幕处理主维度）

```text
1. 处理单元 = 比赛（一场 BO 系列，如 WBG vs LNG BO3）；不是直播间、不是小时窗口。
2. 一场比赛内含多个小局（games[]）：G1/G2/G3 是比赛内部的切片，
   局间切换（G1->G2）不重建比赛，只切换局标签；只有对阵/系列变更才开新比赛。
3. 数据组织：
   - 原始层：docs/data/danmu/<platform>/<日期>_<源>.jsonl 按流/日落盘，永不改写；
   - 切片层：tools/slice_danmu_by_match.py 按比赛维度产出
     docs/data/danmu/slices/<match_id>/all.jsonl（整场）+ game_N.jsonl（逐局）
     + summary.json（条数/活跃用户/窗口/来源/断档>10min 缺口）+ index.json；
   - 清单：docs/data/danmu/slices/manifest.json（比赛 id/对阵/联赛/流/窗口/games）。
4. 比赛窗口来源优先级：官方开赛/结束时间 > 弹幕 GG/比分信号复核 > 报告数据窗口；
   小局窗口须可溯源（官方局间时间或弹幕信号），禁止拍脑袋切局。
5. 一场比赛多个直播间 = 同一切片内多 source 合并（交叉验证），
   summary.sources 记录各源条数；跨比赛的同源流（如官方流连播两场）由窗口切分。
6. 数据缺口纪律：切片 summary 自动检测 >10 分钟断档并记录；
   报告/情报引用切片时必须如实标注缺口（如 TES vs AL 17:32-19:56 断档），
   禁止把"切片窗口"当"完整数据"。
7. 赛后复盘（REVIEW_SCHEMA）与局中情报（LIVE_INTEL_SCHEMA）都按比赛维度组织：
   复盘 games[] 必填（无数据的小局写"样本不足/断档"）；实时情报头部标
   "当前比赛 + 当前小局 + S0-S4 阶段"。
```

## 12. 比赛结束判定校验规则（2026-08-19，防误判）

```text
背景：2026-08-19 曾把观众预测/玩梗（"A队两图晋级了""魔术队赢FUT不意外"）
误判为比赛结果。教训：零散弹幕是观点不是事实。

1. 禁止用零散弹幕下"已结束/比分"结论。单条或少数弹幕可能是预测/玩梗/剧透/情绪。
2. 结束判定需 ≥3 类独立信号共振：
   a) GG/恭喜/结束类弹幕高密度（连续 ≥2 分钟，达到比赛窗口峰值强度的相当比例，
      且不只少数几条）；
   b) 比分/图数信号与直播画面/流标题/官方比分源核对（"2:0"须有对应图数确认）；
   c) 弹幕流量骤降（窗口密度降到峰值的 <10% 并持续 ≥5 分钟）；
   d) 官方/第三方比分源（赛事官网、HLTV、官方房间标题）或主播明确宣布。
3. 语言甄别：
   - 结果陈述："X 赢了 / 2:0 结束 / 恭喜 X"（过去式 + 大量共识 + 无修饰词）；
   - 预测/反讽："X 要赢 / 必 2:0 / 赢 X 不意外 / 暴打 X 就离谱 / 该赢 / 有说法"——
     一律不算结果，按观点记录。
4. 多源交叉：不同直播间同场观点重合才可升置信；单源零散弹幕一律"待确认/进行中"。
5. 误判修正：一旦发现误判，立即把 matches.json result 回退为"进行中/待确认"，
   在记录保留"误判修正"备注（时间+原因），并同步修正受影响报告与汇总文档。
6. 工具：tools/verify_match_end.py 对候选结束时刻做信号打分，
   低于阈值一律输出"未确认（进行中）"，禁止直接当作结果。
7. 盘口/做局俚语禁用词（2026-08-22 教训）："赚了/吃一局/收米/收钱/送温暖/
   水位不动/明演/到点就送/包翻/剧本/卡盘"等为灰信号/盘口情绪词，一律不得作为
   胜负证据；出现时先归入灰信号统计，再找独立结果信号（恭喜/拿下/明确比分/
   官方源）。教训：SK-TH G1 把"sk赚了！/sk今天吃一局/大优势sk还是水位不动"
   误读为 SK 胜，实为 SK 做局输球获利的灰话（TH 胜）。
8. 低样本门槛：单源且比赛窗口弹幕 <800 条时，结果默认"低置信·待确认"，
   除非存在"恭喜/拿下 + 明确比分"类强共识；输出页必须标注置信等级（高/中/低）。
9. 用户异议优先回退：用户对结果提出异议时，先把已输出结论降级为"待确认"，
   重新交叉验证后再修正落库（防错规则第 6 条的执行细则）。
10. 终局窗口锚定（2026-08-23 教训，最高优先级）：结果判定必须以"终局窗口"为锚——
    最后一波/GG/恭喜/结算收盘（如"一波/收汁/减号收了/小33收"）出现并保持 2 分钟无
    反转才算结果。局中任何"XX拿下/XX赢了/1-1了/让一追二"等表述，只要出现在终局
    窗口之前，一律先视为预测/情绪，禁止当结果；终局窗口内的"随随便便2-0/一波/收"
    类信号权重最高。教训：FNC-SHFT G2 把局中预测（"shft拿下"00:20、"假翻 右边
    拿下"00:23、"1:1了"00:15 起）当结果，漏看终局信号（"随随便便2-0"00:31、
    "减号收了/小33收"00:32-35），误判 SHFT 胜；实际 FNC 2:0。
11. 边位映射 + 翻盘方向判定（2026-08-23 二度教训，最高优先级）：
    a) BO3/BO5 每局红蓝边位可互换——"左边/右边/蓝色方"的指代<b>不能跨局沿用</b>，
       必须逐局用"队伍名 + 边位"显式绑定（例：G1"左边大虐sk"→SK=右；G2 需重新确认，
       实际 SK 换到左侧）；无队伍名绑定的左右言论只作情绪，不作定位依据；
    b) "翻了/翻盘/炼金龙翻了/假翻"等只有方向无主体的信号，<b>禁止直接定胜负</b>——
       必须用"赛后归因"确认：被集中批"送/带线/演/冲进去送/送两波"的一方 = 输方
       （被翻方），赢方 = 翻盘方；
    c) 判定顺序：终局窗口（GG/一波）→ 赛后归因（谁被批=输方）→ 队伍名绑定 →
       用户/官方确认，缺一不可；
    d) 教训：SK 场 G2 把"翻了"误读为米人队翻盘成功，实际是 SK（左侧、前期落后）
       翻盘取胜；赛后归因（EZ/supa/jojo/奥拉夫被批"送/带线"=米人队输）本可直接确认。
12. 局间/图间 hype 词禁用为结果（2026-08-23 三度教训，最高优先级）：
    a) 比赛未结束时，"XX冠军了/XX 2:0 了/带走了/稳了/不用看了/直接XX"等
       局间 hype/预测词一律视为情绪，禁止当系列/整场结果；
    b) 系列/整场结果只能等"真正的终局窗口"：最后一小局/图 GG + 赛后确认
       （官方/用户/赛后复盘口径），且与赛果一致才落库；
    c) 局间刷屏（如"绿龙冠军了"03:06-03:09）≠ 系列结束——03:11 图二手枪局
       才刚开，误判即源于此；
    d) 输出时序纪律：小局/图结束才报小局结果；系列结果必须单独等系列终局，
       禁止把小局结束后的 hype 顺延成系列结果。
```
